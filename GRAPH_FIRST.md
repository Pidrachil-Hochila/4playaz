# GRAPH FIRST — читать перед началом любой работы

> **Правило №1.** Перед тем как искать файлы, читать код или менять что-либо в проекте
> 4PLAYAZ — сначала открой граф знаний в `graphify-out/`. Там вся структура проекта
> уже разобрана: какие файлы за что отвечают и как они связаны между собой.

## Зачем

Граф собран скиллом **graphify**. Он экономит время:
- не нужно вслепую грепать по всему репозиторию;
- сразу видно связи между файлами (кто что вызывает, импортирует, тестирует);
- функции и модули уже сгруппированы по смысловым «сообществам».

## Что лежит в `graphify-out/`

| Файл / папка | Что внутри |
|---|---|
| `GRAPH_REPORT.md` | Сводка: список всех сообществ (хабов) с навигацией. **Точка входа.** |
| `graph.json` | Полный граф: узлы и рёбра в машинном виде. |
| `graph.html` | Интерактивная визуализация графа (открыть в браузере). |
| `manifest.json` | Список проиндексированных файлов с хешами (видно, что покрыто графом). |
| `obsidian/` | 251 заметка — по одной на каждый узел (функцию, модуль, константу). |
| `obsidian/_COMMUNITY_*.md` | Описание каждого смыслового кластера и его участников. |

## Порядок работы — всегда

1. **Открыть `graphify-out/GRAPH_REPORT.md`** — найти подходящее сообщество
   (например, `Backend Express Core`, `Admin Auth & Login Security`,
   `YooKassa Payment Processing`, `CDEK Delivery API`, `Cart State Management`).
2. **Открыть нужный `_COMMUNITY_*.md`** в `obsidian/` — посмотреть, какие узлы
   входят в кластер и как они связаны.
3. **Открыть заметку конкретного узла** в `obsidian/` — там путь к файлу,
   роль узла и ссылки `[[...]]` на связанные узлы.
4. Только после этого — переходить к реальным файлам кода и вносить изменения.

## Когда граф устарел

Граф — снимок на момент последней генерации (`manifest.json` хранит хеши файлов).
Если код заметно менялся после этого — перегенерировать граф командой `/graphify`.
Если граф расходится с реальным кодом — **верить коду**, а граф обновить.

## Кратко

Граф — это карта. Код — это территория. Сначала карта, потом территория.
